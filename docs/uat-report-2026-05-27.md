**验收结论**：`BLOCK`

当时存在 3 个 CRITICAL 与 19 个 HIGH 级别问题，不满足放行要求。

---

## CRITICAL 级别（3）

1. `DistributedLockAspect` 存在 SpEL 注入风险，可演化为远程代码执行
2. `RedisLockService` 锁释放存在 TOCTOU 竞争条件
3. 分布式锁时间单位处理不一致，可能导致锁几乎立刻过期

---

## HIGH 级别（19）

### 前端类

- 区块链状态判断受编码损坏影响
- `UserProfile.vue` 绕过统一 Axios 客户端
- 分页参数命名不一致
- 客户端筛选与服务端分页冲突
- 大量中文文案绕过 `i18n`
- 广泛使用 `any`
- 多个 API 返回类型与后端响应不匹配

### 后端服务类

- 多个服务存在 N+1 查询
- 用户详情查询缺少权限控制
- 碳币转账没有锁定双方账户
- 权限切面仅校验权限码存在
- 数据隔离切面实现不完整
- 审计切面虽然注释写异步，实际仍同步落库

### 安全类

- Redis 故障时限流 fail-open
- 前端错误文案存在乱码
- 后端审计文案存在乱码

### API 一致性类

- `credit.ts` 与后端参数传递方式不匹配
- `captcha.ts` 返回类型与后端不匹配
- `carbon.ts` 状态码定义冲突

---

## MEDIUM 级别（30）

主要集中在：

- 搜索框和筛选逻辑未完全真正接入后端
- 类型声明过宽或不一致
- 页面仍有硬编码数据、硬编码比例或状态映射
- 日期解析、分页校验、错误处理方式不稳
- AOP 层存在执行顺序、抖动、脱敏策略等设计瑕疵

---

## LOW 级别（8）

主要是：

- 命名不一致
- 常量未抽取
- 局部重复逻辑
- 个别分页总数写死

---

## 编码损坏专项结论

这份报告明确指出，当时项目中存在一类系统性问题：中文内容在错误编码环境下被写入，形成 mojibake。

重点影响位置包括：

- 前端 API 错误提示
- 管理页状态文案
- 后端审计日志模块名

建议措施：

1. 全仓扫描乱码内容
2. 统一转为 UTF-8
3. 对关键中文提示做回归检查

---

## 架构级观察

1. N+1 查询是系统性问题  
2. 分布式锁实现当时存在多重风险  
3. 数据隔离切面未完整落地  
4. 前后端类型契约曾明显不稳定

---

## 修复优先级建议

1. 先处理 CRITICAL：分布式锁与注入风险
2. 再处理 HIGH：权限、编码损坏、并发安全、API 契约冲突
3. 然后处理 MEDIUM：N+1、i18n、筛选/分页冲突、类型严格化
4. 最后收尾 LOW：命名、常量抽取与轻量重构
